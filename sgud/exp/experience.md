# 累積經驗

本檔為特有之累積經驗,留給後續之嘗試、執行與判斷,由agent自行編列、擴充與維護.

> **兩節分工**(不要互相搬東西,兩者是不同種類的知識):
>
> | | 規則帳本 | 執行經驗 |
> |---|---|---|
> | 講什麼 | **程式碼須長成什麼樣** | **下次動手前該先知道什麼** |
> | 單位 | 規則(非缺陷站點) | 踩過的坑 |
> | 可驗證性 | 每條附可重跑之盤點指令與站點全集,由 `test/unit-ruleSites.test.mjs` 以站點數機械鎖住 | 無指令可盤點,只能靠讀 |
> | 何時查 | 改到某條規則所涉之處時 | **動手前**先掃一遍 |
>
> 判別:寫得出「盤點指令 + 站點數」的進帳本;寫不出、但不知道就會再踩一次的進執行經驗。
> 帳本各條目內之「本條之歷史」為該規則專屬之成因,留在條目內;其中**可轉移到其他規則**的部分才提到執行經驗。

## 執行經驗

> 依「動手前 → 動手中 → 驗收 → 派工」排序。每條附踩過的具體形狀,無形狀者不收。

### 動手前

**E1 軸取自契約,不取自缺陷** —— 本專案重複最多次的一條

三次同一形狀:R8(下載路由軸,成員手寫在五個測試檔內且各檔不一致)、R10(惡意 err 值軸,測試丟的是 `new Error('...')`,正是當初那個缺陷的形狀)、第九輪(無監聽器軸,45 個測試檔全部先註冊監聽器再打路由,**沒有一個打自己沒註冊的路由**)。共同點:**測試照樣全綠**,因為每個檔案都跑完了自己陣列裡的每一個成員。

列軸時的順序不可顛倒:①先問「這條軸的成員,由**契約**推導應該有哪些」②再問「現在測了哪些」③差集就是缺格。反過來做(先看測了什麼再補)永遠補不到沒想到的成員。

**E2 先寫探針,不要推論** —— 我的推論錯誤率不低

第九輪六個假設實測推翻兩個:①`console.log(惡意值)` 會拋錯 → **不會**,Node 的 `util.inspect` 對拋錯的 `Symbol.toStringTag` getter、拋錯 `toString`、已撤銷 Proxy 皆安全;②`pm.reject(new Error(...))` 會被序列化成 `{}` → **不會**,wsemi 序列化為 `"Error: boom"`。同一輪還推翻了我自己規劃裡的設計(見 E3)。

凡「應用端交出惡意值會怎樣」「某 API 的邊界行為如何」一律先寫 `tmp/probe_*.mjs` 實測再下筆。成本是幾分鐘,省下的是一整條錯誤的修正路線。

**E3 自己的修正規劃也要探針驗過**

第九輪原規劃以 `evEmit` 之回傳值判定「有無監聽器」。實測(`tmp/probe_r9_emitret.mjs`)發現 `wsemi/src/evEmit.mjs:107` 在**監聽器拋錯**的 catch 分支也 `return false`,與「無監聽器」不可分辨 —— 而拋錯那格已由 `funSettle` settle 過且發過一則事件,依原規劃會再發一則,**違反 R5**。改以派發前 `ev.listenerCount(name)` 判定。

規劃裡每一個「用 X 來判定 Y」的句子,都要問「X 在哪些情況下會等於 Y 以外的東西」。

**E3b 拿好測的訊號代替難測的事實時,一定要先量兩者的差集** —— 同一輪內犯了兩次

| 難測的事實 | 我拿去代替它的好測訊號 | 差集(實測) |
|---|---|---|
| 「這個事件有沒有人接聽」 | `evEmit` 之回傳值 | 監聽器**拋錯**時也回 `false` → 會對已 settle 過的那格再發一則事件,違反 R5 |
| 「應用端會不會回話」 | 呼叫端斷線之 socket 事件 | 兩者**獨立**:呼叫端在等時它不觸發;應用端正常時它照樣觸發。真正關上的唯一一格是已裁定不修的那格 |
| 「應用端的串流壞了」 | `ERR_STREAM_PREMATURE_CLOSE` | **使用者主動取消下載**產生同一個錯誤碼,不可分辨 → 每次取消都會變成一則 error 事件 |

三次都是同一個形狀,而且**三次都在我自認想清楚之後**。動作:寫下「我要用 X 判 Y」之後,**下一件事就是列出 X 為真而 Y 為假的情形**,並實測。列不出來不代表沒有,代表還沒想到 —— 去寫探針。

**E3c 「能不能判出來」的通用判準**

套件要對某件事負責,前提是**能在確定時點、只用手上的值、不挑任何時間長度把它判出來**。

- 判「**現在的狀態**」可以(如 `listenerCount()` 回 0)。
- 判「**永遠不會發生**」不行 —— 那是對無限未來的斷言,任何有限時點都與「還沒好」不可分辨,而「還沒好」通常是合法狀態。

要處理「永遠不會」只有一條路:**讓有權決定的人畫一條線**(呼叫端傳一個期限),而不是套件自己猜一個。不可分辨之事,本就該由有權決定者畫界。詳見 `sgud/rule/rulebook.md` 之 R12 分界線。

**E4 界定套件責任邊界的判準:該事實的資訊在誰手上**

第九輪裁定「監聽器未註冊」要修、「監聽器註冊了但不 settle pm」不修,分界如下:

| | 未註冊 | 不 settle |
|---|---|---|
| 套件如何得知 | `ev.emit()` **已同步回傳 false**,值已在手上只是被丟棄 | 只能裝計時器並**猜一個值** |
| 性質 | 套件丟棄了自己收到的回傳值 | 應用端函數體內之自有 bug |

後者與「以匿名函數持有參照而使物件無法 GC」同類,無任何函式庫會為此裝設監測;且套件若強制逾時,將與「刻意關閉 server/socket 逾時」「不替使用者決定次數與頻率」兩條既定設計牴觸。**連寫 JSDoc 警語都不該加** —— 加警語等於宣稱套件對此有責任。

推論:不要為了「對稱性」把不同類的兩件事綁在一起做。對稱性只適用於**同類**元素。

**E16 以靜態構造之壞狀態驗修正,修正後該狀態可能根本不可達** —— 第十輪踩過

D1 之探針直接在暫存夾造出「殘檔 + 上一代 `.done`」,據以證明缺陷;草擬之測試也照抄同一個構造。但修正的內容正是「開始合併前先刪 `.done`」—— 修正後這個狀態**不會由套件的任何操作產生**,拿它當測試,修正後照樣紅,而且測的是一個不存在的情境。

- 缺陷若是「某個狀態被錯誤處置」,先問:**修正是讓處置變對,還是讓該狀態不可達?** 後者要測的是**不變式有被維持**(如「push 回傳當下舊標記已不存在」),不是壞狀態的處置。
- 真正的觸發序列(行程於合併途中被殺)要以**子行程序列式**驗收:子行程依真實操作走到那一步後 `process.exit`,父行程再檢查。靜態構造只能當缺陷的證據,不能當修正的驗收。
- 附帶:序列式探針要能在修正前後**都**判讀 —— 本輪的子行程原本盯合併檔的正式名,修正後合併改寫暫存名,探針遂「20s 未觀察到合併進行中」而不可判讀;改為兩個名字擇其存在者觀察。

**E17 規劃裡「放在哪一行」要模擬,不能只寫「做什麼」** —— E3 之延伸

第十輪原規劃 R-A 寫「qPush 開始合併前刪除殘留之 `.done`」。兩份外部複審各自把它**套進 src 的副本實跑**,發現 E2/E4 兩格仍交出殘檔 —— 刪除若放在 qPush 早返(`合併檔與 .done 並存 → no-op`)之後,那一格根本走不到刪除。規劃的每一句「在 X 之前做 Y」,都要問「X 之前有沒有別的出口」;最便宜的驗法是把規劃套到副本上跑一次。

**E30 外部提出之修正建議:「事實屬實」不等於「修法可採」** —— 第十二輪

w-serv-hapi 之 agent 提出四項,四項事實逐條對過 `file:line` 全屬實,但修法有三項各撞一條本套件既有之設計:

| 建議之修法 | 撞到 |
|---|---|
| verifyConn 非函數 →「建構時拋錯」 | 建構期失敗一律走 error 事件、不拋出(第十輪 A13 才把 serverHapi 路由註冊失敗由拋錯改為事件) |
| /ulctr「寫檔前判 listenerCount」(整條) | merge-slices-get 之 S3 冪等與 S2 在途共用;且兩處手寫 listenerCount 破 R12 之單一擁有者 |
| serverHapi 之 stop「只清自有資源」 | hapi 無移除路由之 API —— 改完等於什麼都沒停 |

建議者看的是它自己的套件需要什麼,看不到本套件的既有保證。動作:收到外部修法,對每一條問「它會撞哪條既有規則/保證/上游 API 之限制」,並把修法套到 src 副本上實跑(E17)。

**E31 「await 之後才訂閱事件」之時窗:事件可能在 await 期間就發完了** —— 第十二輪 C 卷 ①-2

`/main`、`/slc` 都在 `await admit`(verifyConn 可為有限時間之 async)之後才 `req.payload.on('end'/'error'/'close')`。前端在這段期間斷線,這些事件已經發過、不會再發 → handler 永不終結、0 則事件,`/slc` 還開了一個永不關閉的寫入 fd。九輪之中斷測試全綠,因為斷線都發生在**訂閱之後**。判法:凡「await 之後才 on(...)」之處,問「這段 await 期間該事件能不能先發生」;補法是**訂閱之後同步檢查狀態**(`destroyed`),同步區段內沒有時窗。另須配一個「本體已送達但未讀取」之對照組 —— 該狀態並非 destroyed,補判不可誤傷。

**E38 橫切規則(如「中止後不再對外輸出」)的正確性要交給邊界,不要交給內部的每個等待點** —— 2026-10-13 審計 run01

前端中止之模擬版 v1 把「判中止」手寫在 8 個等待點;獨立複審找到之 4 個缺口(中止後仍呼叫 cbProgress、仍發 error、以值 resolve、仍呼叫 getToken)**全部是下一個沒被手寫到之站點**。v2 改為兩個擁有者:**入口競速**(公開 promise 與中止競速,中止時尚未 settle 即以 reason 拒絕)+ **呼叫層級之出口守門**(error、cbProgress、console、應用端回呼一律經出口,出口於已中止時不輸出);等待點之判斷降為釋放資源之最佳化,漏判不再是契約缺陷。可轉移的判準:規則若是「某事發生後**對外**不得再有 X」,擁有者就是**所有對外輸出的出口**與**對外的那個 promise**;若規則寫在內部流程的各站點,下一個新增的 await 就會漏。同型之舊例:E15 之「自製保護層自身會長洞」。

**E49 把「結局之分類」交給通用輔助函式,等於引進一份不寫在本套件裡的形狀黑名單** —— 2026-10-14 審計 run01(他套件之建議書)

`callApi` 以 wsemi `pmConvertResolve` 把每次嘗試分成 success/error,而它另有第三態:拒絕值之 `reason === 'cancelled'` 即判為取消、原值丟棄(wsemi 取消家族之慣例,其 JSDoc 明載)。本套件明文「伺服器回傳值不可用形狀白名單」(`classifyFailure` 說明),結果在結局路徑上有一份**黑名單**沒人看見:應用端或 getToken 以 `{reason:'cancelled'}` 拒絕 → `''`、0 則、不重試;惡意值使 `.catch` 內之 `get(msg,'reason')` 拋錯 → 永不 settle + 未處理之 rejection(Node 行程結束)。同一輪又找到第二份:`isNoRetry` 以 `get(msg,'response.status') === 413` 對**任意**失敗值判不重試。十二輪 492 條測試全綠 —— 形狀清單手寫在 `api-executeError` 一檔且沒有這兩個成員(E1 之第四次)。

- 盤點法:列出結局路徑上**每一個檢視失敗值之站點**(誰判、讀了值的什麼),對每一站問「這個值是不是外來的(伺服器轉交之應用端值、應用端回呼之值)?」—— 是,則任何依形狀之分支都是黑名單;輔助函式要讀到它的 `.catch`/判定那幾行,不能只看函式名(`pmConvertResolve` 之名字看不出有第三態)。
- 對標:axios 之取消只認自己建立之 `CanceledError` 上之 `__CANCEL__`、p-retry 之不重試只認自己的 `AbortError` 類別、axios-retry 只讀 AxiosError 之 `code`/`response.status` —— 判「取消/不重試」只用**自建物件之識別**,不碰外來值之形狀。
- 修法之驗收不能只跑現有測試:把方案套到 src 副本(`tmp/cancelled/simA`、`simAB`)後既有 492 條照樣全綠 —— 現有測試對這個類別沒有分辨力,必須另寫形狀軸與行為表(E12)。
- **實作補記(run02)**:依「帳本 → 測試 → 程式」之順序,測試寫完時 src 仍等於 HEAD(`git diff --quiet HEAD -- src` 為證),直接跑即得修前紅(api/unit 20 條),不需 stash 或副本;唯 e2e 於測試時自 src 打包,修前須以 `git show HEAD:src/*` 建 repo 副本跑(`tmp/cancelled/run02/headcopy_run.mjs`,同 E40)。新增之測試 26 條中 23 條修前紅、3 條為守門(修前即綠且應綠)—— 守門要在報告中分開列,否則「修前紅 N 條」會被讀成全部。

**E50 報告裡的計數要由腳本產生,手寫的數字也會錯** —— 2026-10-14 審計 run01

審計回應初稿寫「真 Server+Client 36 格」,`role-writer-validate` 之 L2 腳本自輸出檔取值得 34 —— 同一個錯散在全盤、回應、交接三份共 7 處;方案之行數(+9/−4 等)亦為目測,`git diff --no-index --numstat` 實為 +12/−6。動作:報告中的每個計數(格數、則數、列數、行數)都要能指到一支重跑得出它的腳本(本輪 `tmp/cancelled/validate_claims.mjs`、`matrix_count.mjs`);抓到一處就以 `grep -noE "[0-9]+ ?(格|則|次|處|項|列)"` 掃同類。

**E52 結局類之列軸:除了「失敗從哪來」,還要問「誰還能改這條路上的物件」與「成功是怎麼被證明的」** —— 2026-10-14 審計 run01

自審之表 39 列 351 格、空白 0,獨立複審(Opus 子代理)仍補 9 列,主審自己再補 1 類:①**宿主對共用 axios 預設實例之全域設定**(client 用 `import axios` 之預設實例,宿主之攔截器與 `axios.defaults.validateStatus` 直接作用於本套件 —— 下載 404 被當成功落檔);②**codec 之後之形狀**(應用端物件之 `toJSON` 可產生取消形狀);③**嘗試序列**(取消形狀出現在第 k 次,failTwice 契約即破);④伺服端 `canonProtocolValue` 對拒絕值仍用 `isfun`(同檔 `procApp` 早已改 typeof —— 同一規則兩站點);⑤主審:**成功判定之 fail-open**(下載以「沒有 error 標頭」判成功,網址誤指 SPA 主機時把 HTML 存成檔)。另主審把自己 WebFetch 取得的 p-retry 摘要讀錯(寫成「其餘一律重試」,摘要裡明寫非網路 TypeError 與非 Error 值皆不重試)。

- 列「結局來源」軸時加兩問:**這條路上有沒有共用、可被第三方改的物件**(模組層單例、全域預設、攔截器、環境變數)?**成功是肯定式證明(驗到是本套件之回應)還是否定式推定(沒看到錯誤就算成功)?** 後者遇到任何「不是本套件、但狀態碼 2xx」的回應都會宣稱成功。

- 引用外部來源時,結論句寫完要**逐句對回擷取之原文**(E24 之同型:對標欄不是裝飾)。
- 修法要套到副本跑**全測**:私有 axios 實例在探針上全綠,但副本全測 8 條 `api-clientAbort` 紅 —— 測試以全域攔截器打時窗(E39 之作法),私有實例使掛鉤失效;這是方案之代價,不是測試壞了,要交裁示而不是改測試將就。

### 動手中

**E5 本專案檔案為 CRLF —— 分行一律用 `/\r?\n/`**

踩過:剝註解的正規式以 `'\n'` 分行,每行尾端留下 `\r`;而 JS 的 `.` 不跨行終止符,行尾註解的 `$` 錨不到而**整條正規式失效**,誤報 3 個假陽性。徵狀是「規則明明沒被違反,盤點卻說有」。

第十二輪另踩兩個:①**以 Edit 工具做多行修改後,整檔換行被改成 LF**(單行修改者維持 CRLF),git 因 autocrlf 不顯示差異,只在 `git diff` 時提示「LF will be replaced by CRLF」;②用 Git Bash 之 `grep -c $'\r$'` 檢查 CRLF 會得到「全部是 CRLF」之錯誤結果(E18 之同型)。交付前以 node 讀位元組計 `\r\n` 與孤立 `\n` 之數量,孤立 `\n` 不為 0 者轉回 CRLF;以字串比對原始碼之腳本(變異、盤點)一律換行無關(`\r?\n`)。

2026-10-14 觀察:本輪以 Edit 工具對 CRLF 檔(`src/WConverhpClient.mjs`、`src/WConverhpServer.mjs`、`test/tools/api-axes.mjs`、`ports.mjs`、兩份 CLAUDE*.md)做多行修改,換行皆維持 CRLF(以 node 計數為證)—— 與上段第十二輪之觀察不同,工具行為可能已變;**判準不變:改完一律計數驗證**,不依賴工具之行為。

**E10b 「什麼都沒發生」偵測不到,別想用 try/catch 抓**

套件所有偵測手段都是「發生了某件事 → 攔截它」:`try/catch` 攔拋出、`.catch()` 攔 rejection、`funSettle` 攔監聽器拋錯、串流 `'error'` 攔串流出錯。而以下四種是**非事件**,一則錯誤都不會有:

| 形狀 | 為何攔不到 |
|---|---|
| `verifyConn` 回永不 settle 之 promise | `await m` 不回來,而 `catch` 只攔拋出 |
| 監聽器 `pm.resolve(pending promise)` | Promises/A+ 之採納狀態;應用端確實呼叫了 resolve、監聽器確實存在,每道檢查皆通過 |
| 應用端串流永不 `end` | `pipeline` 之 callback 只在出錯或完成時觸發 |
| 完全無監聽器 | 沒有任何程式碼被執行 |

要偵測非事件只有兩條路:**計時**(需要一個套件無從決定的常數,且與「刻意關閉 server/socket 逾時」牴觸)、或**改為偵測另一件真的會發生的事**(如呼叫端斷線之 socket 事件 —— `/slc` 的 `onAbort` 已在做,三條 RPC 路由沒有)。「無監聽器」是唯一例外:`listenerCount` 可同步查出,不必等。

**測試側之徵狀**:這類缺陷讓測試**逾時**而不是**失敗**,而 `Timeout of 60000ms exceeded` 長得像測試寫壞了,不像產品缺陷 —— 看到逾時先問「是不是產品根本沒回應」。

**E11 wsemi 升版後先跑全測 —— 破壞形式可能是整個測試行程中斷**

wsemi 1.8.91 移除 `evem` 之 `type:'safe'` 時,徵狀是 `Runner._uncaught` → 整個 mocha 行程掛掉,**不是某個測試變紅**。只看「幾個 failing」會誤判為沒事。跑完要確認「有沒有正常印出 passing/failing 統計」。

**E12 新測試要先驗分辨力**

### 判讀

**E23 「預設環境通過」不等於「正確」:時窗型缺陷要注入延遲放大才驗得出**

`/slc` 於 request `end` 即回 done、不等寫入串流 finish,十輪測試全綠、真瀏覽器全綠 —— 因為 SSD 上最後一片 fs.write 的延遲是微秒級,時窗從未被命中。以置換 `fs.createWriteStream` 使 `_write` 延後 400ms 才真正寫入(注意:延後**回呼**不夠,資料仍已在 OS 手上;要延後**寫入本身**),第一次就重現 `merge slices failed`。凡「A 完成之後才能 B」之順序性斷言,驗收要把 A 拉慢到肉眼可見,而不是靠環境剛好來得及。

**E24 自己引的對標要回頭對照結論**

N4 引 multer 作對標,卻做出「就地淨化」的結論 —— 而 multer 恰是「原值 + 另給安全值」。兩位複審者各自指出這一點。對標欄不是裝飾:寫完應然之後,回頭問「我引的那個產品在這一格到底怎麼做」,不一致就是結論錯了或對標選錯了。同輪 A 卷另指出「`beforeRetry` hook 不是通報通道」—— 把不同語意的機制當同一件事引用,對標就變成湊數。

**E25 被懷疑三輪的非缺陷,要把驗證結果寫進帳本或測試註解**

`/main` 之 `req.payload.on('close')` 是空的、而 `/slc` 有 `onAbort` —— 形狀上像缺口,第九、十、十一輪各被重新懷疑並重測一次(本輪 A 卷以四種中斷形狀 × 保留量實測,皆已收斂)。凡實測後判為非缺陷者,若只寫在當輪報告,下一輪就會再花一次探針;寫進帳本的「刻意不套」或測試檔頭,附實測數字,才算結案。同型:`/dwgf` 之 HEAD(hapi 已銷毀來源,連打 5 次無累積)、`checkMerging` 之空 `.catch`(被吞集合 = 應繼續輪詢之集合)。

**E27 抽出一個檔時,把「為什麼它該是一個檔」寫下來;寫不出來的,下一輪就該併回去**

`src/` 一度有 26 個檔,其中 5 個是「只為一個述詞而存在、只被一個檔引用、也沒有任何測試或規則以它為錨」—— `hasPipe` 42 行只為一句 `isfun(v.pipe)`。這類檔讓目錄看起來像一個大系統,實際上只是把一個模組的內部細節攤平。**問題不在於它們存在,而在於沒有人能從檔案本身判斷它能不能動** —— 於是每一輪都得重新盤點「誰引用了誰」。

判準已立為帳本 R20(四選一:多處引用 / 有獨立單元測試 / 是建置輸入 / 是某條規則的單一擁有者)。實務上兩點:

- **併檔之前先查三種錨**:①測試是否 `import` 它(真 import 才算,`readCode('src/x.mjs')` 那種只是讀檔內容,改錨即可)②建置腳本是否以它為 `fpSrc`(本專案三個 worker,併了就無法建置)③帳本的盤點指令是否以它的檔名為錨。三者都沒有才是「沒有理由的檔」。
- **併入後測試會紅,而且紅得對**:`unit-ruleSites` 以檔案為單位計數,併檔必然改變分佈。此時該做的是把錨點改成「函式區段」或「併入後之檔」,而不是把數字調到綠 —— 後者正是帳本維護規則第 6 條說的「總量鎖被繞過」。
- **併檔會把被併檔的 JSDoc 一起帶進計數範圍**:`readCode` 只剝行註解、不剝區塊註解,故被併檔 JSDoc 裡的說明範例(`obj2u8arr({ success: undefined })`)在原檔不被計入、併入後卻成了一個「真站點」。本輪 R3 即因此由 9 變 10。**併檔後第一件事是跑全測,紅的那一條先判斷是「真的多了一個站點」還是「JSDoc 被計入」** —— 兩者的修法完全相反(前者改碼,後者改措辭)。

**E36 帳本宣稱之「機械化保護」也要能指到具體的 it** —— 第十二輪 A 卷 ①-11、B 卷 ①-13

R12 自第九輪起宣稱 upload 兩站點以 `api-noListener` 保護,而該檔檔頭列了 upload、六個 it 卻全是 execute/download;`no listener for event[upload]` 於 test/ 0 命中,三輪無人發現。與 E25(被懷疑多輪之非缺陷要寫進帳本)同族之反面:寫進帳本的「已保護」若無對應之 it,比沒寫更糟 —— 它讓下一個人不再去查。動作:帳本寫「機械化保護」時附 it 標題或可 grep 之斷言字面。另:`tmp/measure_sites.mjs` 仍讀第十一輪併檔前之 `buildDownloadSource.mjs` 而無法執行,`unit-ruleSites` 之提示仍指向它;第十二輪改用 `tmp/r12/sites.mjs`(同 `readCode` 剝註解規則、保留行號)產生逐站點清單。

**E37 上游改了下游會繼承之行為:以 resolve hook 在下游預驗,下游測試以「版號 + 觀察行為」雙條件標 pending** —— 第十二輪之後續(w-serv-hapi,2026-10-13)

本套件第十二輪之上傳閘門與 verifyConn 收緊由 w-serv-hapi 原樣轉傳而繼承,但其 node_modules 為已發布之 2.1.6,本 repo 之版號在發布前也仍是 2.1.6 —— 下游之測試無法單憑版號區分新舊。作法:①下游以 `node --import <register.mjs>`(內以 `module.register` 掛 resolve hook,把 `'w-converhp/...'` 解析到本 repo)預驗繼承之行為,不動其 node_modules,mocha 用 `--no-parallel`;②下游測試於「安裝版號等於已知缺陷之版號」且「觀察到舊行為」時 `this.skip()`,升版後自動成為正式斷言,版號已更新而仍為舊行為即失敗 —— 只看行為會把日後之回歸吞成 pending,只看版號則升版前無法預驗。③對舊版跑對照組要設上限:2.1.6 之伺服器無 upload 監聽時,官方 client 之 upload() 不會結束(實測逾 2 分鐘而中止)。

**E29 「帳本以它為錨」不能當成保留一個檔案的理由 —— 那是循環論證**

第十一輪立 R20(模組須有獨立成檔之理由)時,我列了四種理由,第四種是「**是某條規則之單一擁有者**」,並據此保留了 6 個只被 server 使用、也沒有獨立單元測試的檔。使用者一句「為何 `validDownloadField` 還是獨立成一個檔」就戳破了:**帳本的盤點指令之所以以那個檔名為錨,只是因為它當初就是獨立檔**;併入之後把錨點改成「函式區段」即可,而我自己在同一輪對 `hasPipe` 正是這樣處理的。

可轉移的判準:**當我為某個現況找理由時,先問「這個理由是不是由現況本身產生的」**。「測試這樣寫」「帳本這樣記」「grep 這樣掃」都屬於這一類 —— 它們是我可以改的東西,不是外部約束。真正的外部約束只有三種:別的檔真的需要它(多檔共用)、測試真的需要 import 它(獨立測試)、建置真的讀它(建置輸入)。

同源的一次:同輪把 `retryDelay` 的三個常數匯出,理由是「單元測試要用」—— 那也是我可以改的(改用規格字面值斷言),不是外部約束。**兩次都是把自己造成的相依當成了不可動的前提。**

**E28 改匯出形式這種「全樹機械改動」,三個坑都在「找該改哪裡」的工具形狀上,不在改動本身**

使用者要求各 `.mjs` 統一 `export default`(帳本 R21)。改 4 個檔的匯出 + 15 個檔的匯入,踩到三個坑,全部同型:

| 坑 | 徵狀 | 為何難發現 |
|---|---|---|
| 整檔替換 `export let ` → `let` 少了尾隨空格 | 9 個宣告變成 `letdownloadRoutes` | 壞的是 `test/` 的 fixture,`eslint src/` 不掃它 |
| 盤點具名 import 用單行正規式 | **多行** `import {\n a,\n b\n} from` 整個漏抓 | 全測只少 5 條(354 → 349)且錯誤是 `Uncaught error outside test suite`,不是某條測試紅 |
| 解構行插在其他 import 之前 | `import/first` 6 條 | 只有 eslint 抓得到,測試全綠 |

可轉移的三條:①**批次替換涉及識別字邊界時,替換後當場逐條回驗**(`grep -nE "^let "`),不要等測試;②**掃語法結構不能只用單行正規式** —— import / export / 函式簽章都可能跨行,須另加 `^import {$` 這類多行開頭的 pattern;③**「總數少了幾條」與「某條紅了」是兩種不同的訊號**,前者代表有檔案根本沒載入,要看 `failing` 那一行的內容而不是只看 `passing` 的數字。

E18 講的是「觀察工具會失真」,本條是它在**批次改動**上的具體形狀:改動本身都是機械的、正確的,錯的是我用來決定「改哪裡」的那條 grep。

**E26 統一「取值來源」時,合成值的站點會被靜默抹平,而且舊測試全綠**

六路由之 authorization 有五條取自標頭、一條(`/dwgf`)由 query 之 token **合成**。收斂 `ctxOf` 時若一律「從標頭取」,`/dwgf` 之 verifyConn 會收到空字串 → 以 authorization 授權的應用端,瀏覽器下載管理器路徑全面 403;而 325 條測試無一會紅(fixture 之 verifyConn 都不看 authorization),唯一保護在 e2e。對策不是「小心一點」:①差異寫成表(`routeSpec.authFrom`)而非參數;②收斂**之前**先鋪行為表測試(六路由所見之 authorization),並以「故意改錯 → 紅」驗分辨力;③收斂前後以探針對六路由 × 情境快照狀態碼與標頭集合逐格 diff(本輪 25 格 0 差異)。
